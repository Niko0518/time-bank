## 1. 背景与诊断（代码证据）

v9.27.0 周期内开发者反馈三处明显卡顿，经代码核查，根因**主要在 Web 渲染架构，而非 WebView 平台本身**：

| # | 瓶颈 | 代码证据（需复核） | 影响场景 |
|---|------|-------------------|---------|
| 1 | **主线程重复全量遍历** | `app-reports.js` `getFilteredTransactions`（约 L217-232）：每次调用对 5000 条执行 `filter` + `new Date(t.timestamp)` 解析 + `sort`。全文散落 10+ 处 `transactions.filter()`（约 L25 / L290 / L408 / L632 / L1706） | 报告切换、刷新 |
| 2 | **无派生数据缓存** | `updateAllReports`（约 L73）每次从零重算所有卡片聚合，无记忆化 | 报告页一切操作 |
| 3 | **表格整体重建** | `updateDetailedDataTable` 用字符串拼 `<tr><td>` 全量重渲染（已有 `tableVisibleRows=10` 折叠雏形，见 `collapseTableRows` 约 L7636） | 报告滑动、展开 |
| 4 | **布局抖动** | 卡片展开/收起触发 `refreshReportCardLayout` + masonry 重算（约 L7636 / L8419-8491）；`app-2.js` `toggleCategoryTaskExpand`（约 L1980） | 首页三卡片同时展开/收起 |
| 5 | **合成层过载** | `css/main.css` 有 15+ 处 `backdrop-filter`；通透模式叠加多层 `box-shadow` + `saturate(1.4)` | 通透模式滑动、报告切换 |

**关键判断**：瓶颈 1-4 是架构债（原生重写也会原样带过去），瓶颈 5 部分与平台相关。因此优先级是**先解决架构债（阶段一~二），再压缩合成成本（阶段三）**，原生方案（阶段五~六）仅作后备。

## 3. 阶段一：数据层（P0，最先做）

**目标**：5000 条聚合从"每次 O(N log N) 重算"变为"预解析 + 缓存命中"。

### 3.1 时间戳预解析
- **现状**：热路径里每次过滤都对 5000 条 `new Date(t.timestamp)`，对象分配 + 解析开销大。
- **方案**：数据加载/同步落库时，一次性为每条交易写入数值字段 `_ts`（毫秒时间戳）。所有比较改用 `_ts`。
- **注意**：`_ts` 是派生字段，**不参与云端同步、不参与导出**（或导出时剥离），避免污染数据结构。需在 `loadData`/`saveData`/同步入口处统一注入。
- **验收**：`getFilteredTransactions` 内不再出现 `new Date(`。

### 3.2 派生索引缓存
- **方案**：建立按"上海时区自然日"分桶的 Map 索引（`dayIndex: Map<dateStr, Transaction[]>`），数据变更时置脏重建一次；`getFilteredTransactions` 改为查缓存，key = `period + sortBy + dataVersion`。
- **数据版本号**：引入单调递增的 `dataVersion`，任何增删改交易后 +1。缓存命中条件 = 版本号一致。
- **验收**：同一周期连续两次打开报告页，第二次聚合耗时接近 0（console.time 验证）。

### 3.3 聚合记忆化
- **方案**：`updateAllReports` 内各卡片的 reduce 聚合（日收支 L1716-1717、饼图 L1942/L6262 等）按 `dataVersion + 卡片参数` 缓存结果，未变更不重算。
- **验收**：切换报告周期时，未变更卡片的聚合函数不被重复调用。

### 3.4 Web Worker 下沉（进阶，可选）
- **方案**：饼图聚合、走势统计等纯计算移入 Worker，主线程只接收结果渲染。
- **风险**：数据需结构化克隆传入 Worker，注意 5000 条的序列化成本；建议 3.1-3.3 完成后再评估是否必要。

**阶段一预期收益**：报告切换/刷新耗时下降 60-80%。
**最大风险**：缓存一致性。务必用数据版本号机制，且置脏点覆盖所有写入路径（addTransaction、撤销、同步拉取、导入）。

## 4. 阶段二：渲染层

### 4.1 `content-visibility: auto`（P0 速赢，改动极小）
- **方案**：给报告各 `.report-section` 加 `content-visibility: auto` + `contain-intrinsic-size`，屏幕外卡片跳过渲染。
- **注意**：需测试对 masonry 布局（`applyMasonryLayout`）和卡片高度测量的副作用；若冲突，仅用于长列表行。
- **验收**：报告页首屏渲染耗时下降；滚动时屏幕外卡片不参与布局。

### 4.2 详细数据表格虚拟化/分页（P1）
- **现状**：已有 `tableVisibleRows=10` 折叠，但展开后仍可能一次性建大量 DOM。
- **方案**：扩展为滚动按需加载（IntersectionObserver 触底追加），或限制单次渲染上限。
- **验收**：展开"详细数据"后 DOM 行数始终 ≤ 阈值（如 50）。

### 4.3 DOM 写入批处理 + 布局读写分离（P1）
- **方案**：`innerHTML +=` 改 DocumentFragment 一次性提交；`scrollHeight` 等布局读取与写入分离到不同帧（rAF 包裹），消除强制同步布局。
- **重点位置**：`app-reports.js` 中多处 `content.scrollTop = content.scrollHeight`（约 L2114/L2141/L2245）。

### 4.4 卡片展开动画改造（P1）
- **现状**：高度动画每帧触发布局重排；多卡片同时展开/收起叠加抖动。
- **方案**：高度动画改 `grid-template-rows: 0fr→1fr` 或 `transform` 方案；多卡片状态变更合并到单次 rAF 提交。
- **验收**：三卡片同时展开/收起时帧率稳定（第 5 节度量）。

---

## 5. 阶段三：合成层（通透模式专项）

### 5.1 滚动时降级 blur（P0 速赢）
- **方案**：监听滚动（`app-scroll-container`），滚动中临时调小 `--glass-blur-scale`（或暂停 `backdrop-filter`），停止后（debounce ~150ms）恢复。
- **依据**：`--glass-blur-scale` 已是全局变量（`main.css` 约 L41），所有 blur 均引用它，改一处即可全局生效。
- **验收**：通透模式滑动帧率接近非通透模式；视觉上滚动时轻微"雾化"、停止即恢复。

### 5.2 CSS containment（P1）
- **方案**：卡片加 `contain: layout paint`，把重排重绘限制在卡片内部。
- **注意**：`contain: paint` 会裁切溢出内容，需确认卡片无负 margin/溢出阴影被裁。

### 5.3 精简阴影层 + will-change 纪律（P1）
- **方案**：通透模式多层 `box-shadow` 在滚动态简化为单层；`will-change` 仅对正在动画的元素临时启用。

## 6. 阶段四：度量与验证（贯穿全程）

**没有数据的优化不算完成。**

1. **内置 FPS 监测**：用 `requestAnimationFrame` 计帧，输出平均帧率/掉帧次数（可做成设置页的调试开关，默认关闭）。
2. **Chrome 远程调试**：`chrome://inspect` → Performance 面板抓火焰图（见 AGENTS.md「调试」流程）。
3. **基准指标**（优化前后各测一次，记录到本文档附录）：
   - 报告页切换耗时（ms）
   - 报告页滑动平均帧率（fps）
   - 首页三卡片同时展开/收起帧率（fps）
   - 通透 vs 非通透模式的上述差值
4. **真机验证**：每次 P0 项完成后走 AGENTS.md「安装」流程真机验证，不能只看模拟器。

## 7. 阶段五：混合原生（后备逃生舱）

**触发条件**：阶段一~四完成后真机仍不满足流畅度要求。

- 保留 WebView 主体，仅把最热路径（交易明细列表）改用原生 `RecyclerView` 渲染，经 `WebAppInterface` JS Bridge 通信。
- 收益高，但需设计 Bridge 协议、维护双渲染体系、处理主题/暗色模式同步。
- **实施前必须单独出设计文档，经开发者确认。**

## 8. 阶段六：纯原生重写（战略选项，非本期）

- Compose 全量重写。**触发条件**：数据突破 2 万条 且 阶段一~五全部到顶。
- 本期不做。但阶段一的"数据分层 + 索引 + 版本号"设计天然可复用于未来迁移——这是"先榨干 WebView"与"未来迁原生"不冲突的原因。

## 10. 风险与红线

1. **数据完整性是最高红线**。任何缓存/索引机制必须有可靠的置脏与失效路径；宁可少优化，不可错数据。参考 9.22.0 灾难（`docs/restoring-v9.22.0-optimizations.md`）。
2. **不碰云函数**（`cloudbase-functions/`），不碰同步协议。
3. **不擅自改版本号**。9.28.0 的版本号更新由开发者在推送时指定。
4. **双源镜像纪律**：只在 `assets/www/` 改，推送时才同步根目录。
5. **性能优化易引入回归**：每项改动单独提交、单独验证，便于 `git revert` 定点回退。
