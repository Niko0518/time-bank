# 实时监听（Watch）实现方案

> 结论先行：**Watch 一定能恢复，而且代价很小**——只需给"交易"这一个监听加上滑动时间窗。
> 其余 4 个集合的监听本来就是好的（此前我说"Watch 全挂"不准确，这里更正）。

---

## 一、先把事实摆清（全部实测）

### 1.1 项目现在有 5 个 Watch，挂了 1 个

| 监听 | 注册位置 | 查询条件 | 匹配文档数（实测） | 状态 |
|---|---|---|---|---|
| task | `app-1.js:4769` | `_openid` | 119 | ✅ 正常 |
| **transaction** | `app-1.js:4874` | `_openid` | **6286** | ❌ **超限失败** |
| running | `app-1.js:5002` | `_openid` | 3 | ✅ 正常 |
| profile | `app-1.js:5095` | `_openid` | 5 | ✅ 正常 |
| daily | `app-1.js:5182` | `_openid` | 348 | ✅ 正常 |

真机日志反复出现的 `Exceed max docs number 5000` 只来自 transaction 一路，其余 4 路不受影响（这也解释了为什么"跨设备任务启停"一直比"跨设备交易"灵）。

### 1.2 上限是按"匹配文档数"算的（证据链）

- 该 Watch **已经带了** `where({ _openid })` 条件，仍然失败 → 说明限制不是"集合总数"这么简单；
- 该用户交易 6286 条 > 5000，而其他 4 个集合合计仅 475 条、全部成功；
- 官方文档明确 watch **支持 where 条件**（`db.collection(x).where({...}).watch()`，官方实时推送页示例即此写法）。

⇒ 判定：**上限 = 该监听条件匹配到的文档数**，超过即拒绝建立。

### 1.3 一个决定性推论（让方案变得很简单）

滑动时间窗的匹配数是**稳定**的，不随时间无限增长：

| 窗口 | 匹配数（实测） |
|---|---|
| 近 7 天 | 132 |
| 近 30 天 | 572 |
| 近 90 天 | 2035 |

按当前记录密度（约 22 条/天），**近 30 天窗口稳态就是 550~700 条**；要撑到 5000 需每天 167 笔记录。
⇒ **时间窗方案不是权宜之计，而是长期稳定解**，不需要"窗口自动收窄"那类复杂逻辑。

## 二、方案 W1：交易 Watch 改滑动时间窗（推荐，立即实施）

### 改动（只有 1 处）

```js
// [v9.38.0] 交易 Watch 恢复：实测该用户交易 6286 条 > 平台 5000 匹配上限
// 窗口按"天"动态计算 → 每次重建监听都会自动向前滚动，且稳态匹配数稳定（近 30 天约 572 条）
const TRANSACTION_WATCH_WINDOW_DAYS = 30;
const __winStartIso = new Date(Date.now() - TRANSACTION_WATCH_WINDOW_DAYS * 86400000).toISOString();

watchers.transaction = db.collection(TABLES.TRANSACTION)
    .where({ _openid: currentUid, timestamp: db.command.gte(__winStartIso) })  // ← 只加一个条件
    .watch({
        onChange: (snapshot) => { /* 现有回调逻辑完全不用改 */ }
    });
```

- 位置：`app-1.js` 的 `subscribeAll()`（约 4874 行）
- `timestamp` 有索引（`(_openid, timestamp)` 已建），查询与推送都走索引
- 与存储类型一致：实测 `timestamp` 为 ISO 字符串（7045/7045），故用 ISO 起点比较
- **不加 `orderBy`/`limit`**：官方文档未明确其与 watch 的组合行为，保守起见不动（只加 where）

### 效果

| 场景 | 现在 | W1 之后 |
|---|---|---|
| 本机新增交易 | 立即可见（本地写入） | 不变 |
| **另一台设备新增交易** | 等 10 秒轮询（方案 C） | **亚秒~1 秒推送** |
| 另一台设备修改/撤回交易 | 等 10 秒轮询 | 亚秒推送 |
| 补录 30 天前的旧记录 | 10 秒轮询也**拉不到**（游标漏，见第三节） | 由"全量对账"兜底 |

### 风险与回退

| 风险 | 概率 | 处理 |
|---|---|---|
| 上限其实按"集合总数"算 → 加条件后仍超限 | 低（1.2 证据链支持按匹配数） | 建立失败会自动进入现有重连/降级流程，**10 秒轮询继续兜底**，不会比现在更差 |
| 窗口内记录密度骤增超限 | 极低（需 167 笔/天） | 把窗口从 30 天改为 14 天（匹配数减半）即可 |
| 需要看得更早 | — | 窗口值可调（15/30/60/90 天），或走下面的 W2 |

**回退成本**：一行（删掉 where 里的 timestamp 条件即回到现状）。

## 三、必须同时补的一个洞（否则 W1/C 都不完整）

方案 C（10 秒轮询）与 W1 用的都是**时间游标**（`timestamp >= lastSyncAt`）。这带来一个共同盲区：

> **补录/回填的旧日期记录，其 `timestamp` 小于游标 → 永远拉不到。**

更糟的是：C 上线后 `lastCloudSyncAt` 每 10 秒刷新，导致原有的"120 分钟全量兜底"**永远不会触发**，盲区被放大。

### 修法：加"全量对账"节流（小改动）

```js
// [v9.38.0] 全量对账：每 6 小时至少一次，兜住"补录旧日期"这类时间游标盲区
const FULL_RECONCILE_INTERVAL_MS = 6 * 60 * 60 * 1000;
const lastFullReconcileAt = Number(localStorage.getItem('tb_lastFullReconcileAt') || 0);
if (Date.now() - lastFullReconcileAt > FULL_RECONCILE_INTERVAL_MS) {
    // 走现有的全量路径（DAL.loadAll + 合并），成功后再写入 tb_lastFullReconcileAt
}
```
- 位置：`reconcileCloudAfterWatch()` 内，增量分支之前
- 成本：每 6 小时一次全量（当前 7000+ 条、分页加载），可接受
- 收益：补录、跨端删除残留、任何"时间游标看不到的变更"都会被周期性纠正

## 四、方案 W2：信号集合（彻底解，后续可选）

若想要"任何集合、任何时间、任何变更都能实时触发"，用**单文档信号**：

```
新建 tb_sync_signal（每用户 1 条）
  { _openid, at: <毫秒>, src: 'tx'|'task'|'running'|'profile', seq }

写入侧：前端 DAL 每次写库后 → update 该文档 at=now（1 次极轻量写）
       云函数 tbMutation 写库后 → 同样 update

订阅侧：Watch 只订阅这 1 条文档（匹配数恒为 1，永不超限）
        onChange → 触发已有 reconcileCloudAfterWatch('signal') → 按类型拉增量
```

| 对比 | W1（时间窗） | W2（信号集合） |
|---|---|---|
| 改动面 | `app-1.js` 1 处 | 前端写入点多处 + 云函数 + 新建集合 |
| 实时性 | 窗口内亚秒推送 | 全部变更 1~3 秒 |
| 覆盖面 | 交易 + 其余 4 集合本就正常 | 可统一所有集合 |
| 窗口外变更 | 靠 6 小时对账 | **写时就通知，不漏** |
| 是否需要再拉一次数据 | 否（推送即数据） | 是（信号→再查，多 1 次直连查询，很便宜） |
| 风险 | 仅依赖"匹配数上限"这一判断 | 需保证所有写入点都打点（漏打则漏通知，仍有轮询兜底） |

⇒ **建议 W1 先上（今天就能生效），W2 作为下一版的增强**（等 W1 跑一周，确认"匹配数上限"判断成立、且窗口外变更确实需要实时化时再做）。
